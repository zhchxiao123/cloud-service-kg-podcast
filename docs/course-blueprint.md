# 《本体工程与知识图谱实战》优化版课程蓝图

> 状态：主线课程结构基线
> 适用范围：EP01–EP16
> 目标受众：具备基础 Python 或数据处理经验，希望系统学习本体工程与知识图谱的开发者、研究生和技术工程师

## 1. 课程最终成果

学完主线后，学习者应能独立完成以下任务：

1. 把业务问题整理成可验证的 Competency Questions（CQ）。
2. 使用 RDF、RDFS、OWL 和 SHACL 表达领域知识与约束。
3. 使用 SPARQL 查询 RDF 图，并理解 RDF 与属性图的差异。
4. 从文档中抽取、规范化和链接实体与关系。
5. 将 RDF 映射到 Neo4j，并使用 Cypher 完成应用查询。
6. 在人工审核下使用 LLM 辅助本体和知识图谱构建。
7. 从一致性、约束、CQ 和应用效果四个层面评估知识图谱。
8. 发布一个可运行、可复现、可引用的知识图谱项目。

课程贯穿项目为“云服务选型知识图谱”。项目不等到 EP14 才开始，而是从 EP03 起每集增加一个可验证产物。

## 2. 单集统一结构

主视频保持 8–12 分钟，负责讲清一个核心问题；完整操作放在配套实验中，避免短视频承担过多内容。

每集统一包含：

1. **问题与场景**：为什么需要本集知识。
2. **一个核心模型**：只解释本集最重要的概念。
3. **最小可运行演示**：视频中能看懂、仓库中能复现。
4. **常见误区**：明确概念边界。
5. **项目增量**：为贯穿项目增加一个产物。
6. **验收标准**：学习者如何判断自己做对了。
7. **下一集接口**：本集产物如何成为下一集输入。

建议的配套内容：

- 主视频：8–12 分钟，8–10 张幻灯片。
- 实验视频或 Notebook：15–30 分钟，可选。
- 课后作业：30–60 分钟。
- 参考答案：在下一集发布后公开，避免作业只有题目没有反馈。

## 3. 模块一：从问题到可查询本体（EP01–EP06）

### EP01｜本体到底解决什么问题？

**状态**：已完成；保留现有叙事，后续只补充勘误说明。

**核心问题**：当数据已经存在，AI 为什么仍然不能稳定理解业务？

**学习结果**：

- 区分数据集成问题与语义不一致问题。
- 用自己的话解释本体、知识图谱和应用之间的关系。
- 判断一个场景是否真的需要本体。

**主要内容**：

- 制造业客服跨 ERP、MES、WMS 查询的连续案例。
- 同名异义、异名同义和角色差异。
- 本体提供概念、关系和约束的共享说明。
- 本体是语义增强方案，不是所有 GraphRAG 或 Agent 的必要前提。

**演示**：同一个问题在字段拼接、向量检索和结构化语义查询下的差异。

**项目增量**：建立项目问题陈述和术语候选清单。

**验收标准**：学习者能列出三个语义冲突，并说明它们不是简单改字段名就能解决的问题。

**内容边界**：不讲 RDF 语法，不把单一企业案例指标推广为通用效果。

### EP02｜RDF 三元组：知识的原子单位

**状态**：成片已完成，发布前做术语和衔接修订。

**核心问题**：怎样把“事物及其关系”写成机器可交换的图？

**学习结果**：

- 识别 RDF 三元组的主语、谓语和宾语。
- 区分 IRI、空白节点和字面量。
- 阅读并手写一段最小 Turtle。
- 知道 RDF 是数据模型，RDFS/OWL 用于表达更丰富的语义。

**主要内容**：

- RDF 图与三元组。
- IRI 与命名空间。
- 字面量、数据类型和语言标签。
- Turtle 的 `@prefix`、`a`、`;` 和 `,`。
- Turtle 是序列化格式，Triple Store 才是存储系统。
- 普通 JSON、JSON-LD 与 RDF 的关系。

**演示**：用 RDFLib 解析一段云服务 Turtle，打印三元组数量与内容。

**项目增量**：`ep02/sample.ttl` 和可运行的 RDFLib 校验脚本。

**验收标准**：学习者能写出至少五条有效三元组，并通过解析器校验。

**内容边界**：不讨论 RDF 性能优劣，不展开语句级溯源或复杂的语句具体化（reification）。

**发布前修订**：

- 用 IRI 作为正式术语，URI 只作历史和兼容说明。
- 将“JSON 没有语义”限定为“普通 JSON 的语义通常由应用自行约定”。
- 删除“RDF 查询比数据库慢”的概括。
- 下一集预告改为 CQ，而不是直接进入 Protégé。

### EP03｜先问问题，再画本体：Competency Questions

**核心问题**：怎样知道本体应该包含什么，又怎样判断它是否完成？

**学习结果**：

- 把模糊业务需求改写为具体、可验证的 CQ。
- 区分 Must-have、Should-have 和 Nice-to-have CQ。
- 从 CQ 中识别候选概念、关系、属性和约束。

**主要内容**：

- CQ 的作用：需求、范围和验收标准。
- 好 CQ 的四个条件：具体、有边界、能用数据回答、答案可验证。
- 从自然语言问题提取名词、关系、限定条件和输出形式。
- 反例：“推荐最好的云服务”为什么不是合格 CQ。
- CQ 与查询测试之间的关系。

**演示**：把“帮我选择 GPU 云服务”改写为三条可测试 CQ，并形成映射表。

**项目增量**：`project/docs/competency-questions.md`，包含 6 条核心 CQ、优先级、预期答案形式和所需数据。

**验收标准**：每条 Must-have CQ 都能映射到明确的数据需求，且不存在“最好”“合适”等未定义词。

**下一集接口**：CQ 中的概念和关系成为 Protégé 建模输入。

### EP04｜Protégé 入门：从 CQ 到第一个本体

**核心问题**：如何把 CQ 中的概念和关系变成一个可维护的本体骨架？

**学习结果**：

- 区分类、个体、对象属性、数据属性和注释属性。
- 区分 TBox 与 ABox。
- 在 Protégé 中创建、保存并重新打开一个本体。

**主要内容**：

- 先做概念表，再操作工具。
- 类与个体的粒度：`ComputeService`、`AmazonEC2`、具体 SKU 的区别。
- 对象属性与数据属性。
- Domain/Range 的基本作用及其推理含义。
- 标签、定义、来源和命名规范。

**演示**：根据 EP03 的三条 CQ 创建最小云服务本体，并加入两个服务商、两个服务和两个区域。

**项目增量**：`project/ontology/cloud_service.ttl` v0.1，以及术语表和命名约定。

**验收标准**：

- 至少 6 个类、4 个对象属性、4 个数据属性。
- 所有核心实体具有中英文标签和定义。
- 类与个体没有混用。

**内容边界**：不在本集教授复杂 OWL 限制，也不把 Domain/Range 当作输入校验规则。

### EP05｜OWL 与推理：机器究竟推断出了什么？

**核心问题**：显式事实如何产生隐式知识，又如何发现逻辑矛盾？

**学习结果**：

- 理解子类、等价类、不相交类和存在限制。
- 理解开放世界假设与唯一名称假设。
- 运行推理机并解释推理结果，而不只是展示按钮。

**主要内容**：

- Asserted knowledge 与 inferred knowledge。
- `subClassOf`、`equivalentClass`、`disjointWith`。
- `someValuesFrom` 的直觉解释。
- 开放世界下“没有记录”不代表“值为否”。
- 推理与数据校验的区别。

**演示**：定义 `GPUComputeOffering`，让推理机自动归类一个实例；再用不相交类制造可解释的不一致。

**项目增量**：`reasoning_demo.ttl`、`inconsistent_example.ttl` 和预期推理结果说明。

**验收标准**：学习者能分别指出一条自动分类结果和一条矛盾产生的具体公理。

**下一集接口**：用查询验证本体是否能够回答 CQ。

### EP06｜SPARQL：让 CQ 变成可执行查询

**核心问题**：如何直接查询 RDF 图，并把业务问题变成自动化验收测试？

**学习结果**：

- 编写包含 `PREFIX`、`SELECT`、三元组模式和 `FILTER` 的查询。
- 使用 `OPTIONAL`、聚合和 Property Path 完成常见图查询。
- 把 CQ 映射为 SPARQL 查询与预期结果。

**主要内容**：

- Basic Graph Pattern 是图上的模式匹配。
- 变量、过滤、可选属性和聚合。
- “查不到”与“答案是否为否”的区别。
- SPARQL 查询结果与 RDF 图结果。
- 将查询保存为回归测试。

**演示**：查询支持 GPU 且位于亚太区域的计算服务，并展示缺失数据如何影响结果。

**项目增量**：`project/queries/` 下至少 6 个 `.rq` 文件和预期结果。

**验收标准**：6 条核心 CQ 至少有 4 条能够执行；另外 2 条明确记录缺失的模型或数据。

## 4. 模块二：从文档到可用知识图谱（EP07–EP10）

### EP07｜实体抽取：规则、NER 与 LLM 怎么选？

**核心问题**：如何从云服务文档中找出值得进入知识图谱的实体？

**学习结果**：

- 定义适合项目的实体类型和标注规范。
- 比较规则、通用 NER 和 LLM 结构化抽取。
- 计算实体级 Precision、Recall 和 F1。

**主要内容**：

- Mention 不等于知识图谱实体。
- 通用模型为什么难以识别云服务 SKU。
- LLM 输出必须有 schema、证据跨度和校验。
- 小规模人工金标准的重要性。

**演示**：对同一段云服务文档运行规则基线与 LLM 抽取，逐条比较误报和漏报。

**项目增量**：实体标注指南、20–50 条金标准样本、两种方法的预测结果。

**验收标准**：输出可复算的实体级指标，并保留每个实体的原文证据位置。

### EP08｜关系抽取：从一句话到候选三元组

**核心问题**：抽出的自由文本关系如何映射到受控的本体属性？

**学习结果**：

- 区分开放关系抽取与 schema-guided 抽取。
- 识别关系方向、否定、条件和证据。
- 将自由文本关系规范化为本体属性。

**主要内容**：

- OpenIE 的作用与局限。
- LLM schema-guided JSON 输出。
- 关系方向与主宾语类型约束。
- 证据句、置信度和人工审核状态。
- 不把未知关系强行塞入现有属性。

**演示**：从区域可用性与 GPU 规格文本中抽取候选关系，展示一个方向错误和一个无依据关系。

**项目增量**：候选三元组 JSONL、关系映射表和人工审核记录。

**验收标准**：每条接受的三元组都有证据，且主语、谓语、宾语符合预期类型。

### EP09｜实体链接：名字相同，不代表实体相同

**核心问题**：如何把文本 mention 对到项目中的稳定实体，并处理未知实体？

**学习结果**：

- 理解候选生成、消歧、NIL detection 和别名管理。
- 为领域实体建立规范 IRI 和别名表。
- 避免把服务族、产品和 SKU 链接成同一层级。

**主要内容**：

- Mention、canonical entity 和 external identifier。
- 通用百科 KB 对云服务名称覆盖不足的原因。
- 领域 mini-KB、别名、上下文和类型过滤。
- NIL 实体与待审核队列。
- 链接准确率和候选覆盖率。

**演示**：区分 `EC2`、`P5 instance` 和具体实例规格，并处理一个无法链接的新产品名。

**项目增量**：`entity_catalog.csv`、别名表、链接结果和 NIL 队列。

**验收标准**：每个已链接实体拥有稳定项目 IRI、类型、规范名称和来源。

### EP10｜RDF 与 Neo4j：模型转换后还剩下什么？

**核心问题**：如何把 RDF 导入属性图，并理解转换产生的语义差异？

**学习结果**：

- 区分 RDF 图与 labeled property graph。
- 设计明确的 RDF→属性图映射。
- 使用 n10s 导入 RDF，并用 Cypher回答已有 CQ。

**主要内容**：

- 资源、类型、对象属性和数据属性的映射。
- IRI、标签和命名空间如何保留。
- OWL 语义不会自动等价为 Neo4j 标签。
- SPARQL 与 Cypher 对同一 CQ 的表达对比。
- 自托管 Neo4j、n10s 与版本匹配注意事项。

**演示**：导入项目 TTL，用 SPARQL 和 Cypher 分别查询同一个问题并比较结果。

**项目增量**：Docker 配置、n10s 初始化脚本、导入脚本和 6 条 Cypher 查询。

**验收标准**：导入前后关键实体和关系计数可对账，至少 4 条 CQ 在两种查询路径下结果一致。

## 5. 模块三：LLM、约束与问答（EP11–EP13）

### EP11｜LLM 能自动生成本体吗？

**核心问题**：LLM 适合生成什么，不适合替代什么？

**学习结果**：

- 使用结构化提示生成术语和公理候选。
- 识别关系方向、命名空间、粒度和幻觉问题。
- 建立“生成—解析—验证—人工批准”的流程。

**主要内容**：

- 文档分块与证据绑定。
- 先生成候选模型，再生成 Turtle。
- 语法正确不等于语义正确。
- LLM 不直接写入主本体。
- 记录提示、模型、时间和人工修改。

**演示**：展示同一文档的 LLM 初稿和人工修订版，解释至少三处修改。

**项目增量**：提示模板、原始输出、修订版和差异说明。

**验收标准**：所有合并到主本体的新增项都有来源、理由和审核人。

### EP12｜本体质量：OWL、SHACL、OOPS! 各管什么？

**核心问题**：如何把“看起来没问题”变成可重复执行的质量门禁？

**学习结果**：

- 区分逻辑一致性、数据约束、建模陷阱和业务覆盖。
- 编写并运行 SHACL Shape。
- 把质量检查接入自动化测试。

**主要内容**：

- 推理机：逻辑一致性与分类。
- SHACL：数据是否满足业务形状。
- OOPS!：常见本体建模陷阱。
- CQ 测试：本体是否服务于需求。
- 严重程度、例外和质量报告。

**演示**：让一个缺少 provider 的服务同时通过 OWL 推理但违反 SHACL，说明两类工具的边界。

**项目增量**：核心 Shapes、负面测试数据、质量脚本和 CI 检查。

**验收标准**：至少包含一个预期通过和一个预期失败的测试，失败报告能定位到具体节点和属性。

### EP13｜GraphRAG：先把查询做对，再让 LLM 组织答案

**核心问题**：如何让自然语言问答建立在可验证的图查询结果上？

**学习结果**：

- 区分图构建型 GraphRAG 与已有图上的 Text2Query。
- 为 Text2SPARQL/Text2Cypher 提供受控 schema。
- 校验生成查询，并让答案附带证据。

**主要内容**：

- 自然语言问题分类与查询路由。
- Schema 提示、只读查询和超时限制。
- 生成查询的语法与结果校验。
- 图查询结果不是最终自然语言答案。
- 无答案、数据缺失和查询失败要分开报告。

**演示**：同一个问题生成 Cypher，执行后由 LLM 基于结果回答；再展示一次错误查询的修复。

**项目增量**：最小问答接口、查询日志、失败案例集和 10 条测试问题。

**验收标准**：答案必须能回溯到查询、图中实体和数据来源，不能仅凭模型记忆补充事实。

## 6. 模块四：集成、评估与发布（EP14–EP16）

### EP14｜端到端实战：把各集产物接成流水线

**核心问题**：如何让需求、数据、模型、验证和查询形成一个可重复运行的闭环？

**学习结果**：

- 运行完整但规模受控的 KG 构建流水线。
- 理解每个阶段的输入、输出和失败处理。
- 从原始文档重建项目图。

**主要内容**：

- 数据清单与许可边界。
- 清洗、抽取、链接、映射、审核和 RDF 生成。
- 幂等构建、缓存和中间产物。
- SHACL 门禁与失败队列。
- 导入 Neo4j 并运行冒烟查询。

**演示**：从固定样本文档开始，一条命令生成 TTL、质量报告和查询结果。

**项目增量**：真正可执行的 `pipeline.py`、固定样本、配置文件和复现指南。

**验收标准**：在全新环境中按照 README 能重建相同版本的知识图谱；视频只展示主路径，完整操作放实验。

### EP15｜如何评估知识图谱？

**核心问题**：一个“能运行”的知识图谱，怎样证明它“足够好用”？

**学习结果**：

- 从抽取、本体、数据和应用四个层面选择指标。
- 建立金标准与可重复评估集。
- 避免只报告一个看似漂亮的总分。

**主要内容**：

- 实体与关系抽取 Precision、Recall、F1。
- 实体链接准确率与 NIL 表现。
- 一致性、SHACL 违反和建模陷阱。
- CQ 覆盖率与查询正确率。
- GraphRAG 的答案正确性、证据完整性和失败分类。

**演示**：运行评估脚本，定位一个低分指标，并回到对应流水线阶段修复。

**项目增量**：版本化测试集、评估脚本、基线报告和改进记录。

**验收标准**：每个指标都有数据集、计算方法、版本和失败样例，不能只给目标数字。

### EP16｜发布、引用与持续维护

**核心问题**：如何让项目不仅能展示，还能被别人复现、引用和继续维护？

**学习结果**：

- 选择适合代码、数据和本体的许可证。
- 制作可复现 Release 和引用元数据。
- 建立数据更新、版本迁移和弃用策略。

**主要内容**：

- README、LICENSE、CONTRIBUTING 和 CODE_OF_CONDUCT。
- 本体 IRI、版本 IRI、变更日志与兼容性。
- 数据来源、抓取时间和许可说明。
- CITATION.cff、Zenodo 和 DOI。
